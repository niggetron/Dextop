# W13C Web Research (Keyboard & Desktop UX) — Wave 13 / M7 Report

## Scope inspected
Web-only: official Android/Compose desktop + large-screen input docs, Android keyboard-shortcut skill, pointer-capture game docs, Microsoft PowerToys FancyZones docs, Raycast/command-palette design writeups, Compose accessibility/focus material. No source, builds, or token touched. Target: Redmi Pad Pro 5G, Android 16 (API 36), HyperOS 3, 12.1" 120 Hz tablet, minSdk 33, Kotlin + Compose M3E.

## Findings (P1/P2/P3 with citation, why it matters on Android 16/HyperOS, concrete fix)

**P1 — Shortcut dispatch must use `onPreviewKeyEvent` at the right focus scope, KeyDown-only, repeat-filtered.** Text fields consume keys first, so `onKeyEvent` never sees Ctrl+S / Ctrl+Enter; `onPreviewKeyEvent` on a common ancestor is required. Filter `event.type == KeyEventType.KeyDown` and `nativeKeyEvent.repeatCount == 0`, else commands fire on release and auto-repeat. Attach app-wide shortcuts to root scaffold, screen-wide to screen ancestor, modal ones inside the dialog, contextual ones to the focused surface. Handler nodes must be `focusable()` and actually hold focus (`FocusRequester.requestFocus()`); an invisible focus-stealing root is a documented pitfall. [Android shortcut skill](https://developer.android.com/agents/skills/jetpack-compose/adaptive/references/keyboard_shortcuts), [Compose keyboard actions](https://developer.android.com/develop/ui/compose/touch-input/keyboard-input/commands). Why: HyperOS shell/IME may consume keys; a preview-first, scoped dispatcher gives Dextop deterministic capture. Fix: central `DextopShortcutDispatcher` composable at shell root.

**P1 — Publish shortcuts to Android's Keyboard Shortcuts Helper (Meta+/).** Override `Activity.onProvideKeyboardShortcuts(data, menu, deviceId)`, emit `KeyboardShortcutGroup` + `KeyboardShortcutInfo` (label, keycode, modifier mask); groups show by use case; `requestShowKeyboardShortcuts()` opens it in-app. Keep published entries byte-for-byte in sync with real handlers. [Helper guide](https://developer.android.com/develop/ui/compose/touch-input/keyboard-input/keyboard-shortcuts-helper), [desktop keyboard guidance](https://developer.android.com/design/ui/desktop/guides/interaction/keyboard). Why: Android 16 desktop UX explicitly expects discoverable shortcuts; Meta+/ is the system discovery surface. Fix: auto-generate the Helper groups from the same shortcut table that drives dispatch.

**P1 — Conform to standard shortcuts; Escape = local cancel, not Back.** Required set: Ctrl+S/F/N/O/R, Ctrl+Z / Ctrl+Shift+Z, Ctrl+X/C/V/A, Delete, Ctrl+±/0 zoom, Ctrl+1..9 navigation, Ctrl+Tab cycles, Enter/Shift+Enter/Ctrl+Enter submit, Space play/pause, arrows seek, F fullscreen + Escape exit. "Prefer Ctrl as primary modifier on Android"; never override text-editing shortcuts. [Shortcut skill](https://developer.android.com/agents/skills/jetpack-compose/adaptive/references/keyboard_shortcuts), [large-screen input](https://developer.android.com/develop/ui/compose/touch-input/input-compatibility-on-large-screens). Why: external keyboard on a 12.1" tablet must feel like a desktop; nonstandard bindings break muscle memory and accessibility. Fix: ship the table; allow remap later (Android 16 was flagged adding shortcut customization in system UI — not a public app API, do not depend on it [Android Authority](https://www.androidauthority.com/android-16-customizable-keyboard-shortcuts-3524017/)).

**P1 — `requestPointerCapture()` for a dedicated "PC input" mode, not global capture.** Capture requires the view hierarchy to have focus — cannot be requested in `onCreate`; request on interaction or in `onWindowFocusChanged(hasFocus)`, deliver via `setOnCapturedPointerListener`, release with `releasePointerCapture()` (e.g., to show a menu). Captured events are general motion events; check `SOURCE_CLASS_POINTER`/`SOURCE_MOUSE` and buttons via `ACTION_BUTTON_PRESS`/`getActionButton`, scroll via `ACTION_SCROLL` + `AXIS_HSCROLL`/`AXIS_VSCROLL`. [Mouse input guide](https://developer.android.com/games/playgames/input-mouse), [ChromeOS input compatibility](https://developer.android.com/develop/devices/chromeos/learn/input-compatibility). Why: on tablet, capture is the only way to get relative mouse-look / unconstrained cursor for virtual-display and Wayland backends C/D; blanket capture would break touch. Fix: explicit toggle per desktop session; bind to the focused `AndroidView` surface, isolate behind a versioned adapter, always release on FSM teardown/visibility loss.

**P2 — Right-click, hover, scroll, drag-and-drop are first-class desktop signals on large screens.** Map long-press → right-click via `View.OnContextClickListener`; use hover to change cursor icons/highlight; handle wheel/trackpad scroll on custom components; in multi-window contexts support drag-in/out with `requestDragAndDropPermissions()` and `DRAG_FLAG_GLOBAL`. For raw mousewithout translation, declare `<uses-feature android:name="android.hardware.type.pc" android:required="false" />` so install stays valid on tablets. [Large-screen input](https://developer.android.com/develop/ui/compose/touch-input/input-compatibility-on-large-screens), [mouse input](https://developer.android.com/games/playgames/input-mouse). Why: M7 window management (backends A–E) needs context menus and cross-window DnD; translation mode mangles right-click/wheel. Fix: router that translates these into the 64 KB SPSC input ring with source metadata.

**P2 — FancyZones pattern for window layout: predefined zones + keyboard snap + per-monitor layouts.** Key patterns: `Win+Shift+`` opens editor; override Win+Arrows to move focused window between zones (zone-index vs relative-position); `Win+PgUp/PgDn` cycles windows in a zone; `Win+Ctrl+Alt+N` applies a named layout; canvas editor supports arrow-move (10 px), Ctrl+arrow (1 px), Shift+arrow resize, Ctrl+Tab toggle editor/dialog; Shift-while-drag toggles zone activation. [PowerToys FancyZones](https://learn.microsoft.com/en-us/windows/powertoys/fancyzones). Why: fits Dextop's composited virtual-display backend (C) and on-device windowing — deterministic layouts beat freeform dragging on a 12.1" screen. Fix: implement a `SnapZoneEngine` with persisted layouts in the WAL, keyboard-first zone cycling, and a Shift-drag activator; coexist (don't fight) Android 16's own desktop snap/taskbar.

**P2 — Raycast-style command palette: keyboard-invoked, action-executing, discoverable.** Palette ≠ search: it executes actions; ~50 ms perceived response; shortcuts shown inline on each result (Figma "teaches the keyboard"); compact uniform high-contrast rows for arrow-key scanning; fuzzy match with match highlighting; grouped actions with a secondary action panel; recents/context-aware first results; Esc dismisses. Raycast's stated principles: fast/simple/delightful, keyboard-first layout. [Raycast](https://www.raycast.com/), [palette design guide](https://www.setproduct.com/blog/command-palette-ui-design-guide), [Raycast teardown](https://blakecrosley.com/guides/design/raycast), [Raycast design system](https://aiskill.market/blog/inside-raycasts-design-system). Why: a command palette is the highest-leverage M7 feature for a keyboard-first tablet desktop and avoids deep navigation. Fix: "Dextop Command Palette" bound to Ctrl+K/Ctrl+Space, fed from the same action registry as the shortcut table and Shortcut Helper; <16 ms first-frame, stable ordering, inline shortcut hints.

**P2 — Accessibility: keyboard focus and accessibility (TalkBack) focus are distinct.** Keyboard nav via Tab/Shift+Tab (reading order, RTL-aware) and arrows; focus groups (`Modifier.focusGroup()`) fix tabs/lists where Compose mispredicts order; set initial focus on a primary element (search/primary action) to cut keystrokes; provide distinct, consistent focus indicators (M3 states); trap focus inside modals and allow Escape-only local cancel; every interactive element reachable by keyboard alone. Compose `focusRequester { next = ... }` can override traversal order. [Desktop keyboard guidance](https://developer.android.com/design/ui/desktop/guides/interaction/keyboard), [Compose focus traversal](https://developer.android.com/develop/ui/compose/touch-input/focus/focus-traversal), [large-screen input](https://developer.android.com/develop/ui/compose/touch-input/input-compatibility-on-large-screens), [a11y focus in Compose](https://eevis.codes/blog/2025-07-07/its-all-about-accessibility-focus-and-compose/). Why: a keyboard-first desktop UI must not strand TalkBack/switch users; focus order and visible focus are compliance basics. Fix: enforce M3E focus rings on all focusables, semantic labels on custom surfaces, modal focus trapping, keyboard-only UI acceptance test in M8 QA.

**P3 — Android 16 desktop taskbar is system-owned; avoid fighting it.** Google's desktop windowing (QPR builds) provides resizable windows, taskbar, snapping, multi-desktop; reported system bugs (taskbar reserved bounds lost after right-click, overlaps) live in system UI, not apps. [Developer preview](https://android-developers.googleblog.com/2025/06/developer-preview-enhanced-android-desktop-experiences-connected-displays.html), [desktop UX report](https://ppc.land/android-16-brings-desktop-windowing-to-pixel-and-samsung-phones/), [taskbar bug thread](https://support.google.com/android/thread/431219274/android-16-qpr3-desktop-mode-taskbar-overlaps-app-windows-after-right-clicking-pinned-taskbar-icons?hl=en). Why: Dextop's own shell/taskbar should complement backends A/B/E and degrade gracefully under F rather than duplicate or occlude the system taskbar. Fix: detect desktop-windowing mode; expose Dextop palette/zones as additive overlays inside app bounds.

## Deliverable — concrete M7 patterns

1. **Single `ShortcutRegistry` (source of truth)** → drives (a) `onPreviewKeyEvent` dispatcher, (b) `onProvideKeyboardShortcuts` Helper groups, (c) command-palette entries, (d) UI hints. No duplicated tables.
2. **Dispatcher sketch** (root scaffold, M3E shell):
   ```kotlin
   Box(Modifier.fillMaxSize().focusable().onPreviewKeyEvent { e ->
     if (e.type != KeyEventType.KeyDown || e.nativeKeyEvent.repeatCount > 0) return@onPreviewKeyEvent false
     when {
       e.key == Key.K && e.isCtrlPressed -> { palette.toggle(); true }
       e.key == Key.S && e.isCtrlPressed -> { session.save(); true }
       e.key == Key.Escape -> { if (palette.isOpen) { palette.close(); true } else false }
       else -> false
     }
   })
   ```
3. **Pointer capture adapter** — `PointerCaptureController` with `acquire()/release()`, focus-gated (`onWindowFocusChanged`), per-session, versioned adapter; routes captured motion/button/scroll into the input ring; suppressed for touch-only sessions.
4. **SnapZoneEngine** — FancyZones-style persisted layouts (WAL), Win/Super+Arrow cycling, Shift-drag activation, per-display configs; layout apply is atomic under `DesktopSessionFsm`.
5. **Dextop Command Palette** — Ctrl+K, <50 ms, fuzzy+highlight, inline shortcut labels, grouped actions + secondary action panel, Esc to dismiss, initial focus on query field, high-contrast rows.
6. **Accessibility bar** — M3E focus rings, `focusGroup()` on rails/lists/tabs, modal focus trap, RTL-aware order, TalkBack labels, keyboard-only acceptance test.

## Risks / device testing needed
- HyperOS 3 / Xiaomi may consume or remap global shortcuts and meta keys on the Redmi Pad Pro 5G — verify each binding with a real bt keyboard; Meta+/ helper on non-Meta keyboards.
- Pointer capture focus semantics and release on window/session loss must be verified across backends A/C/D/E; ensure no capture leak on FSM teardown (ties to watchdog).
- Android 16 desktop windowing/taskbar behavior is QPR-dependent and has known system bugs; test Dextop overlays with and without external display.
- Palette latency and zone snapping at 120 Hz on 12.1" panel — Perfetto trace on device; keep compositor work off main looper (cf. BUG-02).
- TalkBack + keyboard plus switch-access with palette open; focus restoration on dismiss.
