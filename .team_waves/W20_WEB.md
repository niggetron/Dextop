# Web Research — Wave 20 Report (Android 16 / HyperOS 3 final compatibility checklist)

## Scope inspected
Web-only; no source edits, no token used. Read-only inspection of Dextop source (`android/app/src/main/kotlin/moe/n4tsu/dextop/*`, `AndroidManifest.xml`, `res/xml/mirror_accessibility_service.xml`) to map existing workarounds. Target: Redmi Pad Pro 5G, Android 16 (API 36), HyperOS 3, 12.1" 120 Hz, arm64-v8a, minSdk 33. "Likely rejected" = fails on stock HyperOS 3 and/or Playreview.

## Findings

### P0 — Hidden-API bypass is technically alive but not a stable contract on 36
- Android 16 ships a newly updated `hiddenapi-flags.csv` (SHA-256 `9102af…38074`); blocklist + `max-target-x` entries are enforced via reflection/JNI as `NoSuchMethodException`/`NoSuchFieldException` (all apps, regardless of target when blocklisted). OEMs may ADD blocklist entries; they cannot remove AOSP ones. Cite: https://developer.android.com/about/versions/16/changes/non-sdk-16 , https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces
- Android 16 explicitly warns that libraries relying on **internal ART structures** may break, and these changes arrive via Google Play system updates independent of platform version. Cite: https://developer.android.com/about/versions/16/behavior-changes-all#art-changes
- `HiddenApiBypass.addHiddenApiExemptions("")` (DisplayTopologyController.kt:536,681; MirrorService.kt:118) uses `Unsafe`+`setHiddenApiExemptions`, which the library documents as stable on Android 10+, and is NOT meta-reflection. But its `LSPass` variant is explicitly "unreliable / can be blocked". Library also requires `dependenciesInfo { includeInApk=false; includeInBundle=false }` or Play review fails. Cite: https://github.com/LSPosed/AndroidHiddenApiBypass
- **Workarounds at risk:** `IWindowManager.mirrorDisplay` (DisplayMirrorBackend.kt:243-263; CapabilityProbe.kt:26-32), `freezeDisplayRotation`/`thawDisplayRotation` (PhoneRotationController.kt:72-122), `DisplayTopology$TreeNode` parcel layout (DisplayTopologyController.kt:681-683), `IVirtualDisplayCallback` (DisplayMirrorBackend.kt:718-721). Verdict: **valid only as versioned, non-fatal best-effort** via `PrivilegedAccess` + capability probe, with public fallback (`ASurfaceControl`/`VirtualDisplayConfig`/`requestPointerCapture`). The "non-fatal rejected hidden call" treatment already present (CHANGELOG.md:18,480) is the right pattern.
- Fix: keep the exemptions adapter behind `PrivilegeGate`; on `NoSuchMethodException`/`NoSuchFieldException` disable that strategy for the session and record it in the WAL; never let a reflection failure abort session start.

### P0 — Restricted settings writes: shell grant + self-enable are likely rejected
- `WRITE_SECURE_SETTINGS` is documented "Not for use by third-party applications" (signature/privileged). Cite: https://developer.android.com/reference/android/Manifest.permission#WRITE_SECURE_SETTINGS
- `pm grant <pkg> WRITE_SECURE_SETTINGS` (MainActivity.kt:1731-1741) frequently fails even from adb shell (`grantRuntimePermission: Neither user 2000 nor current process has android.permission.GRANT_RUNTIME_PERMISSIONS`). Verdict: **likely rejected on stock HyperOS 3**; only valid where the user activates Shizuku/embedded privileged runtime (needs re-consent, not durable). Cite: https://stackoverflow.com/questions/77149279 , https://www.tapatalk.com/groups/macrodroid/granting-write-secure-settings-permission-via-adb-t2923-s40.html
- AOSP `SettingsProvider`: "Global and secure settings are changed only by trusted parties"; writes are validated/persisted per user (`settings_global.xml`/`settings_secure.xml`). Cite: https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/packages/SettingsProvider/src/com/android/providers/settings/SettingsProvider.java
- Writing `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` + `ACCESSIBILITY_ENABLED` to self-enable (MainActivity.kt:1747-1765) is the **most likely rejection**: since Android 13, sideloaded apps are blocked by "Restricted settings" and the user must manually tap **Apps → <app> → ⋮ → Allow restricted settings**; shell `settings put secure enabled_accessibility_services` is reported blocked. Cite: https://support.google.com/android/answer/12623953?hl=en , https://www.esper.io/blog/android-13-sideloading-restriction-harder-malware-abuse-accessibility-apis , https://support.google.com/a/thread/410642609/accessibility?hl=en , https://issuetracker.google.com/issues/407149892
- Direct writes to the 7 `modernKeys` (DesktopEnvironment.kt:145-153) and `enable_freeform_support`/`force_resizable_activities` (DesktopModeConfigurator.kt:62-76,106-116) remain **conditional-valid** only under a genuine privileged grant; HyperOS adds its own keys, re-applies defaults at boot, and may ignore the forced-* values for a *virtual* display (already noted at DesktopEnvironment.kt:236-243). Keep the WAL restore of all 7 keys; treat write rejection as `StrategyAttempt(false)`, not fatal.
- Shell `cmd window set-display-windowing-mode` / `wm set-display-windowing-mode` / `cmd activity_task …` (DesktopModeConfigurator.kt:127-153) and `wm set-display-engagement-mode` (:118-125) are **conditional-valid** (privileged shell only), OEM-dependent; keep probe + structured-concurrency re-apply (BUG-02 fix is correct).

### P1 — Foreground services: `specialUse` technically valid, Play-rejection risk
- `LinuxRuntimeService`, `EmbeddedPairingService`, `LinuxSessionService` (AndroidManifest.xml:47-53,95-102,327-334) all declare `foregroundServiceType="specialUse"` + `FOREGROUND_SERVICE_SPECIAL_USE`. Android 14+ requires the declared type + matching permission before `startForeground()`; `specialUse` has no runtime prereq but requires a `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` justification **reviewed in Play Console**. Cite: https://developer.android.com/about/versions/14/changes/fgs-types-required#special-use , https://developer.android.com/develop/background-work/services/fgs/service-types
- Justification strings "Linux services that keep running after the app is closed" / "Linux container session" are generic keep-alives — exactly the pattern Play's device-and-network-abuse policy targets. Cite: https://support.google.com/googleplay/android-developer/answer/13392821
- Android 16: jobs started from an FGS now adhere to runtime quotas (`OVERRIDE_QUOTA_ENFORCEMENT_TO_FGS_JOBS`); background start restrictions still apply. Cite: https://developer.android.com/develop/background-work/services/fgs/changes , https://developer.android.com/about/versions/16/behavior-changes-all#job-quota-opt
- Fix: keep `specialUse` but make each subtype concrete (e.g. "active desktop session with visible ongoing notification"), stop the pairing FGS promptly (consider `shortService`, 3-min cap), and do not rely on FGS to exempt session jobs from quotas. Verdict: manifest form **valid**; Play acceptance **P1 likely rejected** as written.

### P1 — 16 KB page size: current native payload is the release blocker
- Google Play requires all apps targeting 15+ to support 16 KB pages on 64-bit; **from Feb 1, 2027 updates that don't support 16 KB cannot be released** (deadline ~2 months from today). Cite: https://developer.android.com/guide/practices/page-sizes
- Android 16 adds a 16 KB backcompat mode for 4 KB-aligned apps with a user warning dialog (`android:pageSizeCompat` suppresses it). In Android 17 backcompat can be set fatal. Backcompat is explicitly "not best for reliability/stability". Cite: https://developer.android.com/about/versions/16/behavior-changes-all#16-kb-compatibility-mode
- Requirements: `LOAD` segments `>= 2**14`, `GNU_RELRO` end `(VirtAddr+MemSiz) % 0x4000 == 0`, `zipalign -c -P 16`, NDK r28 (or `-Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384` on r27-), uncompressed `.so` via AGP >= 8.5.1. Cite: https://developer.android.com/guide/practices/page-sizes#elf-alignment
- Code assumptions to fix: remove `PAGE_SIZE` (undefined on NDK r27+ in 16 KB mode), use `getpagesize()`/`sysconf(_SC_PAGESIZE)` for `mmap`/`madvise`, scale custom-allocator purge thresholds, zero on `free()`. Cite: https://developer.android.com/guide/practices/page-sizes#check-code , https://developer.android.com/guide/practices/page-sizes#custom-allocators
- Dextop surface: `libdextop_core.so`, PRoot/fastpath/preload C, PulseAudio binaries, 64 KB SPSC ring, and third_party/libffi dlmalloc (page-size based granularity). Verdict: **likely rejected by Play as-is**; must rebuild + `check_elf_alignment.sh` gate in CI before release.

### P1 — Accessibility service constraints
- Besides restricted-settings enablement: `res/xml/mirror_accessibility_service.xml:3-7` requests `flagRequestFilterKeyEvents`, `flagSendMotionEvents`, `flagRetrieveInteractiveWindows`, `canRetrieveWindowContent="true"` — powerful flags that require explicit user consent (>restricted setting) and are a Play-review red flag for a non-accessibility app.
- Android 16 deprecates `announceForAccessibility` / `TYPE_ANNOUNCEMENT` (all apps); use `setAccessibilityPaneTitle`/live regions. Cite: https://developer.android.com/about/versions/16/behavior-changes-all#disruptive-a11y
- Targeting 36 enables predictive back by default: `onBackPressed` and `KeyEvent.KEYCODE_BACK` are no longer dispatched. Dextop's key-event capture via `flagRequestFilterKeyEvents` must be retested — back handling may be swallowed by the system. Opt-out `android:enableOnBackInvokedCallback="false"` is temporary (gone at API 37). Cite: https://developer.android.com/about/versions/16/behavior-changes-16#predictive-back
- Verdict: service declaration **valid**; self-enable **likely rejected**; key-event interception needs device verification.

### P2 — Redmi Pad Pro 5G / HyperOS 3 specifics
- Hardware: 12.1" 2.5K 120 Hz (16:10), Snapdragon 7s Gen 2, arm64-v8a — confirmed by Xiaomi. Cite: https://www.mi.com/global/product/redmi-pad-pro/specs/
- 12.1" => `sw >= 600dp`: for target 36, `screenOrientation`, `resizeableActivity`, `min/maxAspectRatio`, `setRequestedOrientation()`/`getRequestedOrientation()` are **ignored** on large screens (opt-out `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` is temporary, gone at 37). Dextop's `PhoneRotationController` rotation freeze + forced orientation assumptions lose effect; expect more activity re-creation/state loss. Cite: https://developer.android.com/about/versions/16/behavior-changes-16#adaptive-layouts
- HyperOS has a non-AOSP `com.android.server.display.SecondaryDisplayPolicy` that forces external displays into 1:1 mirroring, and single-display SystemUI; turning an external monitor into a real second display requires LSPosed hooks into system_server/SystemUI + `SECONDARY_HOME` + `mirror_built_in_display=0`. Dextop's C=composited **virtual** display avoids this policy, but it cannot inherit Xiaomi's native multi-app desktop without such hooks — this bounds backend E ("scoped OEM") expectations. Cite: https://github.com/the-marox/HyperDesktopUnlock
- HyperOS is reported to reset forced display metrics (README.md:164) and has an external-display bug when "Enable freeform windows on secondary display" is on. Cite: https://new.c.mi.com/uk/post/51875
- HyperOS 3 rollout for Redmi Pad Pro is scheduled Dec–Mar; device is already listed by the community as running Android 16 / HyperOS 3.0 (`OS3.0.301.0.WOJMIXM`, `rodin`) in README.md:152-153. Cite: https://www.reddit.com/r/RedmiPadPro/comments/1qzvorz/hyperos_3_for_redmi_pad_pro/
- Android 16 "virtual device owner overrides" (ignore orientation/aspect/resizability) apply only to trusted/privileged owners — not a third-party escape hatch. Cite: https://developer.android.com/about/versions/16/behavior-changes-all#virtual-device-owner-overrides
- 16 KB page size on this Exact SKU is unconfirmed — must probe `adb shell getconf PAGE_SIZE` on device; do not assume 4 KB.
