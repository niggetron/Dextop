## Findings

**P0 — `$/` is valid and is REQUIRED for a green PR gate here (do not "fix" it back to `./`)**
- `uses: $/.github/workflows/release-apk.yml` in `manual-release.yml:81`, `release.yml:110`, `beta-release.yml:85` is GitHub's official "self-repository" syntax, announced 2026-07-30: resolves to the workflow's own repo at the **running commit**, no checkout, no `@ref`, works for reusable-workflow calls. Available on github.com; **requires runner ≥ 2.336.0**; not on GHES. [GitHub Changelog](https://github.blog/changelog/2026-07-30-reference-same-repository-actions-with-self-repository-syntax) · [Workflow syntax `jobs.<id>.uses`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_iduses) · [Reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) · [runner v2.336.0 release notes](https://github.com/actions/runner/releases/tag/v2.336.0) ("feat: add self-repository action reference syntax").
- This repo runs `runs-on: ubuntu-latest` (github-hosted) everywhere → runner floor satisfied. `safety.yml:84` runs zizmor 1.32.0, whose `self-repository` audit (since v1.30) **flags `./` and recommends `$/`**; reverting to `./` makes the Workflows job fail. [zizmor audits](https://docs.zizmor.sh/audits#self-repository). Field evidence of a real github.com hosted run resolving a reusable workflow via `$/` (run 35611352058, conclusion=success) — with caveat that early rollout used an org `actions_self_repository` flag; now GA on github.com. [SBB issue #114](https://github.com/SchweizerischeBundesbahnen/github-workflows-polarion/issues/114).
- `safety.yml` does **not** run actionlint (grep confirms); actionlint ≤1.7.12 rejects `$/` ([rhysd/actionlint#711](https://github.com/rhysd/actionlint/issues/711)) but that is not a gate. Newer kjanat/actionlint models it. pinact treats `$/` as a pin.

**P2 — release-please config is valid; the release-please *path* is not a one-shot publisher as wired**
- Config validity: every key in `.github/release-please/config.json` is schema-valid (`$schema`, `release-type`, `include-component-in-tag`, `pull-request-title-pattern`, `changelog-sections`, `packages` with `package-name`/`changelog-path`/`prerelease`/`versioning`/`prerelease-type`). [schema](https://raw.githubusercontent.com/googleapis/release-please/main/schemas/config.json). Note: `versioning` (not the older `versioning-strategy`) is the correct manifest-config key — `extractReleaserConfig()` reads `config['versioning']` and merges root defaults into `.`. [manifest.ts](https://raw.githubusercontent.com/googleapis/release-please/main/src/manifest.ts). `versioning: prerelease` is a real strategy; `prerelease: true` + `prerelease-type: beta` yields `2.0.0-beta.N` and marks the Release as prerelease; `include-component-in-tag: false` → tags `v<version>`, matching manual-release. [customizing.md](https://github.com/googleapis/release-please/blob/main/docs/customizing.md) · [manifest-releaser.md](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md) · [versioning-strategy-factory.ts](https://github.com/googleapis/release-please/blob/main/src/factories/versioning-strategy-factory.ts).
- Action v5 inputs `config-file`/`manifest-file`/`token` and root outputs `tag_name`/`version` are valid; but it needs repo setting "Allow GitHub Actions to create and approve pull requests" (or `DEXTOP_RELEASE_APP_ID`/`KEY`), and GITHUB_TOKEN-created PRs do not trigger downstream workflows. [action README](https://github.com/googleapis/release-please-action) · [GITHUB_TOKEN triggers](https://docs.github.com/en/actions/concepts/security/github_token).
- `release.yml:3-7` is `workflow_dispatch`-only: the push that merges the release PR runs nothing, so `released_tag` is normally empty and `release.yml:101-113` APK job is skipped. A plain dispatch only opens/updates the PR. Fix (if this path is wanted): restore `push: [main]` alongside `workflow_dispatch`, or delete its `release-apk` job and document manual-release as the only publisher. (Confirms W21 P2.)

**P2 — manual-release `workflow_dispatch` is mechanically sound (the reliable publisher)**
- `workflow_dispatch` inputs arrive in `inputs` (booleans stay boolean); trigger only exists when the workflow file is on the default branch; `github.sha` = last commit on `GITHUB_REF` branch → tagging HEAD on a dispatch from `main` is correct. [events-that-trigger-workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch) · [triggering-a-workflow](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow).
- `permissions: {}` zeroes all scopes; `publish`/`release-apk` job blocks re-grant `contents: write` — exactly enough for `gh release create` (docs: `contents: write` "allows the action to create a release"). Reusable workflow's `github.token` inherits caller job permissions. [workflow syntax `permissions`](https://docs.github.com/actions/reference/workflow-syntax-for-github-actions#permissions) · [GITHUB_TOKEN tutorial](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).
- `gh` is preinstalled on hosted runners; `gh release create "$tag" --target "$SHA" --notes-file ... --prerelease` creates the tag at the dispatched commit and a Release; `gh release upload --clobber` attaches the APK; `gh release edit --notes-file` rewrites notes. [gh release create](https://cli.github.com/manual/gh_release_create). `workflow_dispatch` is exempt from the "GITHUB_TOKEN events don't start runs" rule, so no event chaining is needed — as the workflow header claims.

**P3 — minor config/citation caveats**
- `changelog-sections` `type: deps` never matches Dependabot's `chore(deps):` commits (they land in "Upgraded" via `chore`); harmless dead entry.
- `manifest.json` = `2.0.0-beta.4`; verify tag `v2.0.0-beta.4` exists before a release-please run (W21 P3 / W20 version-skew unresolved).

## Deliverable — final release path (confirmed, github.com / runner ≥2.336.0)
Green PR gate = `safety.yml` only: gitleaks clean, `zizmor --offline` clean (⇒ `$/` + job-scoped perms + SHA-pinned external actions; `./` fails), `pinact run --check` clean; `macos-compat.yml` excluded. **No actionlint in gate.**

Supported publishing: dispatch **`manual-release.yml`** on `main` (stable/prerelease toggle) — single run creates `v<version>` tag + Release at `github.sha`, then calls `release-apk.yml` via `$/` to build/attach the arm64 debug APK. For betas use **`beta-release.yml`** (same `$/` call, passes `version_code=base+1`). **Do not use `release.yml` as the publisher** unless `push: [main]` is restored; it is dispatch-only and normally yields no tag. All three require `permissions: {}` + per-job `contents: write`; the `$/` calls resolve at the running commit and are the only form accepted by zizmor 1.32.0.
