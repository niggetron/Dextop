# Web Agent W14C — Wave 14 Report (M7 desktop features research)

## Scope inspected
Web-only research on five M7-relevant protocols/ecosystems: (1) xdg-desktop-portal FileChooser, (2) Wayland `wl_data_device` clipboard, (3) Android DocumentsUI/SAF URI permissions, (4) cross-OS clipboard sync patterns, (5) Rust VT100 parsing crates. No builds, no source edits, no token. All claims cited inline.

## Findings

### P2 — FileChooser portal is async handle/Response; backends must emit `file://` URIs
- `OpenFile/SaveFile/SaveFiles(parent_window, title, options a{sv}) -> handle o`; options incl. `handle_token`, `multiple`, `directory`, `filters`, `current_folder`; backend returns `uris as`, `writable b`, `choices` via `results a{sv}`. Results URIs **must** be normalized to `file://`; unnormalizable ones discarded. Selected files may be added to the Documents portal and stay accessible across sessions. [FileChooser](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.FileChooser.html), [impl.FileChooser](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.impl.portal.FileChooser.html), [XML](https://github.com/flatpak/xdg-desktop-portal/blob/main/data/org.freedesktop.portal.FileChooser.xml)
- The call is **not** a simple return: reply is a `Request` object; completion arrives via `Response(response u, results a{sv})` signal (0=ok, 1=cancel, 2=other). Handle format `/org/freedesktop/portal/desktop/request/SENDER/TOKEN`; subscribe to Response **before** calling to avoid a race; verify returned handle; `Close()` aborts. Token must be unguessable/per-library-random. [Request](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Request.html)
- Why it matters: on D (Wayland Linux Mode B) and F (compat), Linux guests (Flatpak) expect this D-Bus contract. A naive synchronous wrapper will lose the Response and hang. Concrete fix: model as a Rust `oneshot`/`StateFlow`-style future keyed by `(sender, token)`, with a timeout and explicit cancel path; treat returned URIs as untrusted strings (reject non-`file://`, non-normalized).

### P2 — Wayland clipboard is lazy FD pipe transfer gated by focus/seat
- Copy: `wl_data_device_manager.create_data_source()` → `wl_data_source.offer(mime)` ×N → `wl_data_device.set_selection()`. Paste: client receives `wl_data_device.data_offer` (then `data_offer.offer` per MIME) followed by `selection`; calls `wl_data_offer.receive(mime, fd)`; source gets `wl_data_source.send(mime, fd)` and writes, then closes. Data travels **directly source→target via a pipe**, no compositor copy. [Wayland book](https://wayland.freedesktop.org/docs/book/Protocol.html), [emersion](https://emersion.fr/blog/2020/wayland-clipboard-drag-and-drop), [wayland.xml](https://chromium.googlesource.com/external/wayland/wayland/+/refs/heads/master/protocol/wayland.xml), [Rust `wl_data_offer`](https://docs.rs/wayland-client/latest/wayland_client/protocol/wl_data_offer/struct.WlDataOffer.html)
- Only the **focused** client receives selection offers (prevents background clipboard snooping); clipboard is per-`wl_seat`; data is an offer, not a stored copy — source closing can lose it. Blocking writes in `send` can stall the event loop; use non-blocking writes. [emersion](https://emersion.fr/blog/2020/wayland-clipboard-drag-and-drop), [WhyNotHugo](https://whynothugo.nl/journal/2022/10/21/how-the-clipboard-works)
- Newer alternative: `org.freedesktop.portal.Clipboard` (v1) extends Remote Desktop / Input Capture sessions; `RequestClipboard()` before `Start()`, `SetSelection(mime_types)`, `SelectionOwnerChanged`, `SelectionRead(mime)->fd`, `SelectionTransfer`+`SelectionWrite/WriteDone`; file transfer via `application/vnd.portal.filetransfer`. **This is the natural fit for Dextop's M6 remote-desktop/input-capture session** — prefer it over raw `wl_data_device` where available. [Clipboard portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Clipboard.html)
- Why it matters: Dextop already has a M6 Wayland data plane; clipboard must bridge this lazy offer model to Android's stored-clip model. Concrete fix: cache the FD contents into an owned buffer as soon as `receive` completes (don't hold offers across source exit); cap size; ignore all MIME except `UTF8_STRING`/`text/plain` for M7; bind to same seat as input.

### P1 — SAF URI grants are per-package and time-scoped; no raw paths
- `ACTION_OPEN_DOCUMENT`/`ACTION_CREATE_DOCUMENT`/`ACTION_OPEN_DOCUMENT_TREE` → `content://` URI; read/write via `ContentResolver`, not `File`. Grants: temporary via `FLAG_GRANT_READ/WRITE_URI_PERMISSION` (lifetime of activity/target), persistent via `takePersistableUriPermission()` (survives reboot; stored in `/data/system/urigrants.xml`; list via `persistedUriPermissions`). Flags grant access to the URI, not the whole provider; package-visibility into the provider's app is also granted. [SAF guide](https://developer.android.com/guide/topics/providers/document-provider), [content-provider-basics](https://developer.android.com/guide/topics/providers/content-provider-basics), [DocumentsContract](https://developer.android.com/reference/android/provider/DocumentsContract), [Kai SAF notes](https://xckevin.github.io/en/blog/android-storage-access-framework), [cleanor SAF](https://cleanor.app/reference/storage-access-framework)
- `DocumentsUI` (`com.android.documentsui`) is a **modular system app** (Android 10+), interacts with framework only through stable `@SystemApi` (no `@hide`), `MANAGE_DOCUMENTS` is signature-protected; RRO theming for OEMs. [AOSP DocumentsUI](https://source.android.com/docs/core/ota/modular-system/documentsui)
- DocumentsProvider hardening: verify `callingPackage` signature/name before `queryChildDocuments`/`openDocument`/`createDocument`/`deleteDocument`; expose only minimum `COLUMN_FLAGS` (avoid `FLAG_SUPPORTS_DELETE` unless needed); `FLAG_SUPPORTS_WRITE` triggers read+write grant on the doc URI. [LY Corporation blog](https://techblog.lycorp.co.jp/ja/blog/20240828a)
- `FileProvider` alternative for app-owned files: `getUriForFile()` -> `content://authority/...`; grant via `Context.grantUriPermission(pkg, uri, flags)` until `revokeUriPermission()`/reboot, or via intent flags. [FileProvider](https://developer.android.com/reference/androidx/core/content/FileProvider)
- Why it matters on HyperOS 3/API 36: a portal `file://` path cannot be handed to a guest as a Linux path if the underlying file lives behind SAF; and a `content://` URI returned to the desktop side is useless without an explicit grant to Dextop's package. Concrete fix: an adapter that (a) uses `ACTION_OPEN_DOCUMENT_TREE` + `takePersistableUriPermission` for a user-chosen Dextop folder, (b) stores URIs (never paths) in the WAL, (c) on each guest open, grants a one-shot read/write grant to the guest-facing provider only after an `openFile` request, (d) validates calling package. No `MANAGE_EXTERNAL_STORAGE`.

### P1 — Android→desktop clipboard cannot be passive; clipboard access is toast-gated and recently restricted
- Clipboard is a single `ClipData` (text/URI/intent), one at a time; paste must check `ClipDescription` MIME types; `getPrimaryClip()` triggers an "APP pasted from your clipboard" toast on API 31+ (suppressed for own app/metadata-only reads); API 33+ copy UI, and `ClipDescription.EXTRA_IS_SENSITIVE` to suppress preview. [Copy/paste guide](https://developer.android.com/guide/topics/text/copy-paste)
- Real-world cross-OS patterns converge on: desktop→Android automatic (write via `setPrimaryClip`), Android→desktop **manual/tap or Shizuku/accessibility/ADB** (background clipboard reads blocked). Examples: Anchor (tap "Send to Desktop" because Android can't read clipboard in background; text+PNG, 1 MB cap) [Anchor](https://anchor-software.org/docs/clipboard-sync); Sefirah (auto-detect via Shizuku/ADB, accessibility fallback) [Sefirah](https://github.com/shrimqy/Sefirah); LinuxDrop (Shizuku + wl-clipboard, AES-256-GCM E2E) [LinuxDrop](https://github.com/burakgon/linuxdrop); clip-sync/ClipSync (LSPosed hook of `setPrimaryClipInternalLocked` to bypass background limits) [clipsync](https://github.com/lcebot/clipsync); ClipRelay (Accessibility for auto-copy) [cliprelay](https://github.com/geekflyer/cliprelay); Huawei cross-device pasteboard (system service syncs, app unaware) [Huawei](https://developer.huawei.com/consumer/en/doc/best-practices/bpta-distributed-pasteboard).
- Why it matters: any M7 "seamless clipboard" promise that requires silent background reads will fail on stock Android 16/HyperOS. Concrete fix: M7 ships **desktop→Android automatic + Android→desktop explicit user action** (share action / persistent notification / QS tile / foreground "Send" button); treat Shizuku/ADB/accessibility as optional versioned adapters gated by `PrivilegeGate`, never required; size-cap (≤1 MiB) and allowlist MIME to text/plain + PNG.

### P2 — VT100 crates: pick `vte` for parsing, `vt100` for screen state; both stable
- `vte` 0.15.0 (Alacritty-maintained, Apache/MIT): implements Paul Williams' ANSI parser state machine; provides `Parser` + `Perform` trait (`print`, `execute`, `csi_dispatch`, `osc_dispatch`, `esc_dispatch`, `hook/put/unhook`, `terminated`); UTF-8 input, OSC terminated by BEL, 7-bit only. `terminated` + `advance_until_terminated` supports synchronized updates. [vte](https://docs.rs/vte/latest/vte/), [Perform](https://docs.rs/vte/latest/vte/trait.Perform.html), [alacritty/vte](https://github.com/alacritty/vte)
- `vt100` 0.18.1 (doy, MIT, MSRV 1.85, ~3.8k SLoC): full in-memory screen (`Parser::process`, `screen()`, `contents_formatted()`, `contents_diff()`), built on `vte`; 0.16.0 added `process_cb` callbacks incl. **OSC 52 clipboard manipulation**, window-resize requests, dim, CNL/CPL. `vt100-ctt` is a less-maintained fork (MSRV 1.70). `vtparse` 0.7 is low-level only and points users to `termwiz`. [vt100](https://docs.rs/vt100/latest/vt100), [crates.io](https://crates.io/crates/vt100), [changelog](https://github.com/doy/vt100-rust/blob/main/CHANGELOG.md), [vtparse](https://docs.rs/vtparse/latest/vtparse)
- Why it matters: M7 terminal emulator needs both an escape parser and a screen model. Concrete fix: `vte` in `libdextop_core.so` for streaming bytes into a `Perform` impl (small, battle-tested, no screen allocation on hot path); use `vt100` only if a full screen buffer is needed, pin exact version, cap scrollback; route OSC 52 writes to the same clipboard bridge as P1/P2 findings (with size cap + user consent). Do not hand-roll a VT parser.

## Deliverable — minimal safe design for Dextop M7

Three thin adapters behind the FSM, no hidden APIs:

1. **File chooser** — one `FileChooserGateway` trait with two impls: Android = `ACTION_OPEN_DOCUMENT[_TREE]` + `takePersistableUriPermission`, persist **URIs only** in the atomic WAL; Wayland/portal = D-Bus `org.freedesktop.portal.FileChooser` with pre-subscribed `Response`, unguessable `handle_token`, timeout+cancel, reject non-`file://`. Normalize both to a neutral `DextopFileRef { scheme, opaque_id, display_name, mime, writable }`. For guest ↦ host, gate each open through a `FileProvider`-style grant to a single stable calling package; verify caller signature.
2. **Clipboard** — owned `ClipboardService` in Rust core with a hard size cap (≤1 MiB) and MIME allowlist (`text/plain;charset=utf-8`, `text/uri-list`, `image/png`). Host side: `ClipboardManager.setPrimaryClip` (auto receive) and explicit "Send to desktop" for Android→guest. Guest side: prefer `org.freedesktop.portal.Clipboard` on the M6 RemoteDesktop/InputCapture session; fall back to raw `wl_data_device` with immediate FD→owned-buffer drain. OSC 52 from the terminal maps into the same service, disabled by default. All cross-device transport is E2E (AES-256-GCM) behind `PrivilegeGate`.
3. **Terminal** — `vte` streaming parser + minimal `Perform` in Rust core; `vt100` optional behind feature flag for full screen; no parser in Kotlin. Wire OSC 52 to service #2 only with explicit consent.
