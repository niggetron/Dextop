# Web/CI Compliance — Wave 21 Report

## Scope inspected
`.github/workflows/{release-apk,manual-release,release,beta-release,debug-apk,safety}.yml`, `.team_waves/W20_RELEASE.md`. Web only: current GitHub Docs (reuse/permissions/triggers/syntax), zizmor 1.32.0 docs+source, pinact 5.0.2 docs, GitHub release/tag API metadata. No source edits, no token.

## Findings

**P1 — Node 20 actions are past runner EOL (removed 2026-09-23) and only survive via forced Node 24.**
`release-apk.yml:68,75,82,150` pin checkout v4.4.0, setup-java v4.9.1, flutter-action v2.23.0, upload-artifact v4.6.2; `manual-release.yml:38` and `safety.yml:33,62` likewise. GitHub made Node 24 default 2026-06-16 and removed Node 20 from runners 2026-09-23; Node 20-targeting actions now emit "may not work as expected" warnings and run only through the compatibility force. Current majors: checkout v7.0.1, setup-java v6.3.0, upload-artifact v7.0.2. Fix: repin to Node 24 majors with pinact, re-verify SHA↔tag comments. https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/ , https://api.github.com/repos/actions/checkout/releases/latest , https://api.github.com/repos/actions/setup-java/releases/latest , https://api.github.com/repos/actions/upload-artifact/releases/latest

**P2 — direct `workflow_dispatch` of release-apk.yml has no concurrency guard.**
`release-apk.yml:57-58` omits concurrency by design because callers serialize on `android-gradle`. Verified: `manual-release.yml:23-25`, `beta-release.yml:16-19`, `release.yml:13-17`, `debug-apk.yml:12-16` all now use `group: android-gradle, cancel-in-progress: false` — W20's P2 claim (`release-${{ github.ref }}` / `beta-release`) is stale/already fixed. But a directly dispatched run is unguarded: two runs with the same `tag` collide on artifact name `dextop-arm64-debug-${{ inputs.tag }}` and race on `gh release upload --clobber` / `gh release edit`. Fix: add `concurrency: {group: android-gradle, cancel-in-progress: false}` to release-apk.yml; safe because GitHub only self-cancels when caller *and* callee use `cancel-in-progress: true` with the same group. https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations

**P2 — Gradle/Flutter cache reads in the publishing job; add `cache-mode: none`.**
`release-apk.yml:79,86`: `actions/setup-java cache: gradle`, `subosito/flutter-action cache: true`. zizmor 1.32.0 does not flag this file today (trigger is `workflow_call`/`workflow_dispatch`, and no "known publisher action" is used), but its audit guidance says release workflows should not read the shared Actions cache — the same cache is written by lower-trust jobs. Fix: `jobs.build.cache-mode: none` on release-apk.yml (fully suppresses the cache-poisoning audit). https://docs.zizmor.sh/audits/#cache-poisoning

**P2 — permission boundary relies on workflow-level inheritance only.**
`release-apk.yml:54-55` declares `permissions: contents: write`; callers set it at workflow level but their reusable-call jobs (`manual-release.yml:74-82`, `release.yml:101-110`, `beta-release.yml:65-73`) omit job-level `permissions`. Legal today (caller grants `contents: write`), but docs say a calling job without a `permissions` block gives the callee the repo *default* permissions, and the callee can only maintain/reduce — a future caller without `contents: write` triggers a validation error ("requesting contents: write, only allowed …") and `gh release upload` 403. Fix: declare `permissions: contents: write` explicitly on each `release-apk` caller job. https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations , https://www.kenmuse.com/blog/github-actions-workflow-permissions/#reusable-workflows

**P2 — safety check has pinning blind spots.**
`safety.yml:84-85`: `zizmor --offline` disables all GitHub-API audits (stale-action-refs, ref-confusion, impostor-commit, archived-uses); `pinact run --check` verifies only full-length SHA syntax — SHA↔version-comment verification needs `--verify-comment`. Spot-checked pins are clean: zizmor 1.32.0 (`bb110cc…`), pinact 5.0.2 (`7f003d8…`), checkout v4.4.0 (`11d5960…`), setup-java v4.9.1 (`cf277c6…`) all match official tag/release asset digests. Fix: add `--verify-comment` and either run an online audit job or document the offline tradeoff. https://docs.zizmor.sh/usage/ , https://github.com/suzuki-shunsuke/pinact/blob/main/docs/check.md , https://api.github.com/repos/zizmorcore/zizmor/releases/latest , https://api.github.com/repos/suzuki-shunsuke/pinact/releases/latest

**P3 — persona-only findings (no default-CI failure).** `undocumented-permissions` (bare `contents: write` without inline rationale) and `concurrency-limits` (`cancel-in-progress: false`) fire under `--persona=pedantic`. Fix: add inline `# needed to create/upload release` comments if pedantic mode is adopted. https://docs.zizmor.sh/audits/#undocumented-permissions

## Deliverable (verified rules + citations)
- **Reusable workflows**: `workflow_call` + `workflow_dispatch` in one file is valid; same-repo `uses: ./.github/workflows/…` resolves to the caller's commit; `workflow_dispatch` only fires from the default branch; max 10 nesting levels. https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows
- **Permissions**: caller-passed `GITHUB_TOKEN` scopes can only be maintained or reduced by the callee; when the calling job has no `permissions`, the callee gets repo defaults. https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations
- **GITHUB_TOKEN release upload**: `contents: write` permits creating/editing releases and uploading assets; GITHUB_TOKEN-triggered events do not create workflow runs except `workflow_dispatch`/`repository_dispatch` — calling release-apk.yml via `uses:` instead of a `release:` trigger is the correct 2026 design. https://docs.github.com/en/actions/tutorials/authenticate-with-github_token , https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows
- **Concurrency**: no concurrency group in the called workflow is acceptable with `cancel-in-progress: false` in callers; only matching groups with `cancel-in-progress: true` self-cancel. (same reusing-workflow-configurations URL)
- **zizmor/pinact**: versions pinned in `safety.yml:17-20` are current (zizmor 1.32.0 published 2026-11-02; pinact 5.0.2 published 2026-10-25); all `uses:` are SHA-pinned with version comments, all `actions/checkout` steps set `persist-credentials: false`, no dangerous triggers (`pull_request_target`/`workflow_run`/`issue_comment`) — no default-persona failure found. https://docs.zizmor.sh/audits/ , https://github.com/suzuki-shunsuke/pinact
